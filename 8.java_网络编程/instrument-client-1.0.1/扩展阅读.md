# 网络编程的难点与需要考虑的问题

网络编程的难点不在于建立 Socket 连接，而在于面对网络不可靠、数据流不完整、并发不可控、资源有限和故障难以预测等情况时，仍然保证程序正确、稳定、安全地运行。

结合当前 Java 仪表通信客户端项目，可以将需要考虑的问题整理为以下几个方面。

## 一、网络编程的核心难点

| 难点     | 典型问题                | 需要解决的核心问题       | 本项目对应实现 |
| ------ | ------------------- | --------------- | --------------- |
| 连接管理   | 连接失败、断连、连接被重置       | 如何建立、维护、关闭连接    | `TcpConnection` + `ConnectionState` 状态机 |
| 数据传输   | 半包、粘包、分批到达          | 如何准确还原完整消息      | `LineProtocol.Decoder` / `LengthFieldProtocol.Decoder` |
| 请求响应   | 响应乱序、响应延迟、响应丢失      | 如何将响应匹配到正确请求    | `RequestManager` + `ResponseMatcher` |
| 超时处理   | 连接超时、响应超时、读写阻塞      | 如何限制等待时间并及时释放资源 | `Duration timeout` + `PendingRequest.future().get(timeout)` |
| 异常恢复   | 网络抖动、设备重启、临时故障      | 如何检测故障并恢复通信     | `ReconnectPolicy` + 指数退避 + 抖动 |
| 并发控制   | 多线程同时发送、关闭与发送竞争     | 如何保证线程安全和状态一致   | `requestLock` + `lifecycleLock` + `volatile` |
| 重试机制   | 重复发送命令、重复执行操作       | 如何避免重复副作用       | `CommandIdempotency` 幂等性标记 |
| 资源管理   | Socket、线程、缓冲区、任务未释放 | 如何保证资源最终释放      | `close()` 终态保护 + `shutdownExecutorGracefully()` |
| 协议解析   | 长度错误、非法帧、噪声数据       | 如何校验数据并从异常数据中恢复 | `ProtocolDecoder` + `maxFrameLength` + 校验和 |
| 安全性    | 非法输入、资源耗尽、数据泄露      | 如何限制输入并保护通信     | 有界队列 + `OverflowPolicy` + 日志脱敏 |
| 性能与稳定性 | 队列堆积、内存增长、线程阻塞      | 如何控制资源使用和系统负载   | `ArrayBlockingQueue` + `LongAdder` 无锁指标 |
| 可观测性   | 无法判断断连原因、请求为何超时     | 如何记录日志、指标和故障原因  | `ClientMetrics` + `ClientDiagnostics` |

## 二、具体需要考虑的问题

### 1. 连接管理

TCP 连接并不是建立一次就可以永久使用，需要考虑连接的完整生命周期。

- 连接超时如何设置？→ `ClientConfig.connectTimeout()`
- 对端关闭连接后，客户端如何感知？→ `Receiver` 读取返回 -1 或 IOException
- 网络断开后，连接状态如何更新？→ `onReceiverFailure()` → `ConnectionState.DISCONNECTED`
- 连接关闭、重连和新连接建立是否可能并发发生？→ `lifecycleLock` 串行化
- 连接失败后，是否需要自动重连？→ `ReconnectPolicy` + `reconnectScheduled` CAS 防重入
- 程序关闭时，如何确保连接和后台线程全部退出？→ `close()` 终态保护 + 线程池优雅关闭

关键原则：连接状态必须明确，不能仅通过一个 `isConnected()` 判断连接是否真正可用。

**本项目的做法**：`TcpConnection.isConnected()` 同时检查逻辑状态 `state == CONNECTED` 和 Socket 物理状态 `socket.isConnected() && !socket.isClosed()`，双重校验确保一致性。

### 2. TCP 数据边界：半包与粘包

TCP 是面向字节流的协议，不保留应用层消息边界。

半包：一条消息分多次到达

```
第 1 次：AA BB
第 2 次：CC DD
```

必须缓存数据，直到完整消息到达。

粘包：多条消息一次到达

```
AA BB CC DD EE FF
```

必须根据协议规则拆分出多条独立消息。

常见解决方案：

- 固定长度协议：每条消息长度固定。
- 分隔符协议：例如以 `\r\n` 作为消息结束标志。→ **本项目 `LineProtocol`**
- 长度字段协议：通过消息头中的长度字段确定消息边界。→ **本项目 `LengthFieldProtocol`**
- 帧校验：校验魔数、长度、校验和等字段。→ **本项目 STX=0xAA + XOR 校验和**

还需要考虑缓冲区扩容、最大帧长度、非法长度、缓冲区残留以及错误数据后的重新同步。

**本项目的做法**：
- `LineProtocol.Decoder`：使用 `ByteArrayOutputStream` 缓存不完整数据，逐个查找分隔符，处理半包和粘包。
- `LengthFieldProtocol.Decoder`：使用 `ByteBuffer` 的 flip/compact 模式管理读写位置，处理半帧累积和多帧拆分。

### 3. 请求与响应匹配

仪表通信经常需要发送命令并等待对应响应。

需要考虑：

- 多个请求同时发送时，如何匹配各自的响应？→ **本项目限制：同一连接同一时刻只允许一个 pending 请求**
- 响应先到、后到或乱序到达时如何处理？→ `ResponseMatcher` 可以拒绝不匹配的响应，保留 pending 继续等待
- 请求超时后，迟到的响应如何处理？→ 超时移除 pending，迟到响应进入异步队列 → `DataListener`
- 收到无法匹配的响应时，应该丢弃、记录还是交给异步事件处理器？→ 进入异步队列 + `DataListener.onData()`
- 同一仪表是否允许多个请求并发执行？→ 协议没有请求 ID，不支持安全并发请求

**本项目的做法**：`RequestManager` 使用 `AtomicReference<PendingRequest>` 管理单个 pending 请求，`requestLock` 保证"检查 → 注册 → 写入"的原子性。`ResponseMatcher` 是函数式接口，支持 `any()`、`contains()`、`equalsText()`、`regex()`、`predicate()` 等匹配策略。

### 4. 超时与重试

超时和重试是最容易引发隐性故障的部分。

| 场景    | 需要注意的问题             | 本项目处理方式 |
| ----- | ------------------- | ---------- |
| 连接超时  | 防止连接建立无限等待          | `Socket.connect(addr, timeoutMillis)` |
| 响应超时  | 请求长时间得不到响应时如何结束等待   | `pending.future().get(timeout, NANOSECONDS)` |
| 写入超时  | 阻塞写入可能无法仅靠读取超时控制    | SO_TIMEOUT 仅影响 read，write 阻塞由 TCP 窗口控制 |
| 重试次数  | 设置最大次数，避免无限重试       | `ReconnectConfig.maxAttempts()` |
| 重试间隔  | 使用退避策略，避免故障期间持续冲击设备 | 指数退避：`initialDelay × 2^(attempt-1)` |
| 超时后重试 | 旧响应可能在新请求发送后到达      | 超时移除 pending，旧响应进入异步队列 |
| 重试副作用 | 命令可能已经执行，只是响应丢失     | `CommandIdempotency` 区分幂等/非幂等 |

尤其需要注意：**超时不等于命令执行失败**。

例如，客户端发送"启动设备"命令后没有收到响应，设备可能已经启动。如果直接重试，就可能造成重复执行。

因此应区分：

- 可安全重试的查询命令 → `IDEMPOTENT`：连接异常时自动重连重试
- 具有重复执行风险的控制命令 → `NON_IDEMPOTENT`：任何异常直接抛出
- 不确定的命令 → `UNKNOWN`：默认不重试

### 5. 并发与线程安全

网络客户端通常存在多个并发角色：

| 角色 | 职责 | 线程安全机制 |
|------|------|------------|
| 业务线程 | 发送命令、管理连接 | `requestLock` 保护请求原子性 |
| Receiver 线程 | 持续读取数据并解码分发 | `ProtocolDecoder.synchronized` 保护解码状态 |
| 重连调度线程 | 执行退避延迟后重连 | `lifecycleLock` 保护连接状态 |
| 请求执行线程池 | 执行 `requestAsync()` | 委托给 `request()`，复用其锁保护 |
| 关闭操作 | 释放所有资源 | `closed` volatile 终态 + CAS |

需要考虑以下竞争情况：

- 两个线程同时发起重连 → `reconnectScheduled` CAS 保证只有一个重连任务
- 发送请求时连接恰好关闭 → `lifecycleLock` 串行化，写入失败触发 `onReceiverFailure()`
- 响应到达时请求刚好超时 → `PendingRequest.tryComplete()` CAS 防止重复完成
- 请求注册与数据发送之间发生异常 → `requestLock` 保护"注册 → 写入"原子性
- 客户端关闭后仍有任务提交 → `closed` volatile 终态检查
- 多线程同时写入导致协议帧交错 → `requestLock` 串行化写入

解决这些问题需要明确线程模型、状态转换、锁的范围、请求生命周期以及关闭过程中的并发约束，而不是简单地给所有方法添加 `synchronized`。

**本项目的做法**：双锁策略——`requestLock`（公平锁）保护请求级操作，`lifecycleLock`（公平锁）保护连接生命周期。`volatile` 保证跨线程可见性，`AtomicBoolean`/`AtomicReference` 保证 CAS 原子操作。

### 6. 资源管理

网络程序需要明确每类资源的所有者和释放时机。

| 资源     | 常见风险      | 处理方式              | 本项目实现 |
| ------ | --------- | ----------------- | -------- |
| Socket | 异常路径未关闭   | 统一管理连接生命周期        | `TcpConnection.close()` + `closeQuietly()` |
| 接收线程   | 关闭后仍然阻塞   | 关闭 Socket 并等待线程退出 | `Receiver.stop()` + Socket 关闭唤醒 read |
| 线程池    | 任务堆积、无法退出 | 有界队列、拒绝策略、明确关闭    | `shutdownExecutorGracefully()` |
| 待处理请求  | 超时后仍保留    | 完成、超时、取消时清理       | `RequestManager.fail()` / `remove()` |
| 缓冲区    | 无限制扩容     | 限制最大缓存和帧长度        | `maxFrameLength` + `ProtocolException` |
| 监听器    | 长期持有对象引用  | 提供注册、移除机制         | `CopyOnWriteArrayList` |
| 重连任务   | 关闭后继续重连   | 取消任务并检查关闭状态       | `closed` + `reconnectSuppressed` 双重检查 |

需要保证正常路径、异常路径、超时路径和并发关闭路径都能够正确释放资源。

**本项目的做法**：`close()` 方法按严格顺序释放资源——设置终态标志 → 停止重连 → 停止接收线程 → 关闭连接 → 重置解码器 → 失败所有 pending 请求 → 关闭线程池。线程池关闭使用 `shutdown()` + `awaitTermination(3s)` + `shutdownNow()` 的优雅关闭模式。

### 7. 协议解析与异常数据恢复

协议解析不能假设对端永远发送合法数据。

需要考虑：

- 魔数不匹配时如何跳过噪声 → `LengthFieldProtocol` 查找 STX=0xAA
- 长度字段小于最小长度或超过最大长度时如何处理 → 抛出 `ProtocolException`
- 校验和错误时是否丢弃当前帧 → 抛出 `ProtocolException`
- 数据不完整时如何保留缓存 → `ByteBuffer.compact()` / `ByteArrayOutputStream` 保留未处理数据
- 连续收到非法数据时如何限制 CPU 消耗 → `maxFrameLength` 限制
- 解析器如何避免无限循环 → 每次处理至少消费 1 字节
- 缓冲区满后如何扩容或清理 → `ensureCapacity()` 扩容
- 恢复同步时如何避免丢弃下一帧的有效起始字节 → 扫描查找下一个 STX

协议解析器应当有明确的输入边界、输出规则、异常策略和缓存上限。

### 8. 性能与可观测性

系统不仅要能正常通信，还需要在故障时能够定位问题。

**本项目提供的可观测能力**：

`ClientMetrics`（无锁指标收集，基于 `LongAdder`）：

| 指标 | 含义 |
|------|------|
| `sentFrames` / `sentBytes` | 发送帧数和字节数 |
| `receivedFrames` | 接收总帧数 |
| `matchedFrames` | 匹配到 pending 请求的帧数 |
| `asyncFrames` | 异步帧数（无法匹配的响应） |
| `droppedAsync` | 丢弃的异步帧数 |
| `listenerErrors` | 监听器回调错误次数 |
| `reconnects` | 重连次数 |
| `timeouts` | 超时次数 |

`ClientDiagnostics`（诊断报告）：

- 连接状态变化历史
- 最近请求记录（命令、时间戳、延迟、成功/失败）
- 错误统计和最后错误信息
- 重连计数

日志应避免直接输出密码、敏感参数或完整的敏感业务数据；同时需要控制日志频率，避免高频错误造成额外负载。

## 三、针对当前 Java 仪表客户端的重点

如果按生产级要求排查，建议优先处理以下问题：

1. **协议正确性**：半包、粘包、非法长度、噪声恢复、缓冲区最大容量 → `ProtocolDecoder` 实现
2. **请求生命周期**：请求注册、发送、响应匹配、超时、迟到响应和取消清理 → `RequestManager` + `PendingRequest`
3. **连接与重连**：连接状态一致性、重复重连、断连恢复和关闭期间的竞态 → `lifecycleLock` + `reconnectScheduled` CAS
4. **并发安全**：并发发送、请求超时与响应竞争、发送与关闭竞争 → `requestLock` + `lifecycleLock`
5. **重试安全性**：区分查询与控制命令，明确重试策略和命令幂等性 → `CommandIdempotency`
6. **资源释放**：Socket、接收线程、线程池、待处理请求和定时任务 → `close()` 终态保护
7. **故障测试**：模拟断网、设备重启、延迟响应、响应丢失、非法数据和并发关闭 → 集成测试

## 五、总结

网络编程可以归纳为六个核心问题：

**连接是否可靠、数据是否完整、请求是否匹配、并发是否安全、故障是否可恢复、资源是否能释放。**

对仪表通信客户端而言，最关键的不是单纯实现 Socket 收发，而是为协议解析、请求生命周期、连接状态、重试策略和资源管理建立清晰且可验证的规则。

# 常见网络编程范式

### 1. BIO（Blocking I/O）— 本项目采用

**模型**：每个连接独占一个线程，读写操作阻塞直到完成。

```
Thread-1 ──→ Socket.read() ──→ [阻塞等待数据] ──→ 处理响应
Thread-2 ──→ Socket.read() ──→ [阻塞等待数据] ──→ 处理响应
```

**特点**：

- 编程简单，逻辑直观
- 线程数 = 连接数，连接多时线程开销大
- 适合连接数少、长连接的场景

**本项目的应用**：

- `TcpConnection` 使用 `Socket.getInputStream()/getOutputStream()` 进行阻塞读写
- `Receiver` 在独立线程中循环调用 `connection.read(buffer)`，阻塞等待数据
- 适合仪器通信场景（通常只有 1~N 个连接，N < 100）

**Java API**：`java.net.Socket`、`java.io.InputStream`、`java.io.OutputStream`

### 2. NIO（Non-blocking I/O / Selector 模型）

**模型**：使用 `Selector` 多路复用多个 Channel 的 I/O 事件，单线程或少量线程即可管理大量连接。

```
Thread-1 ──→ Selector.select() ──→ [有事件的 Channel] ──→ 处理读写
              ↑                        ↓
              └──────── 循环等待 ──────┘
```

**特点**：

- 单线程可管理成千上万连接
- 编程复杂，需要手动处理状态机
- 适合高并发、短连接的场景（如 Web 服务器）

**Java API**：`java.nio.channels.SocketChannel`、`Selector`、`SelectionKey`

**核心概念**：

| 概念 | 说明 |
|------|------|
| Channel | 通道，类似 Socket，支持非阻塞模式 |
| Buffer | 数据容器，NIO 读写都通过 Buffer（本项目 `LengthFieldProtocol.Decoder` 已使用） |
| Selector | 多路复用器，轮询 Channel 的 I/O 就绪事件 |
| SelectionKey | 注册在 Selector 上的 Channel 兴趣事件（OP_READ/OP_WRITE/OP_CONNECT/OP_ACCEPT） |

### 3. AIO（Asynchronous I/O / 异步 I/O）

**模型**：发起 I/O 操作后立即返回，操作系统完成后通过回调通知应用。

```
Thread-1 ──→ channel.read(buffer, callback) ──→ 继续做其他事
                                                ↓
                              OS 完成读取后回调 callback.handleResult()
```

**特点**：

- 真正的异步，不阻塞任何线程
- Windows 下基于 IOCP 表现良好，Linux 下底层支持不如 epoll
- 编程模型复杂，回调嵌套深

**Java API**：`java.nio.channels.AsynchronousSocketChannel`、`CompletionHandler`

### 4. Reactor 模式

**模型**：事件驱动架构，将 I/O 多路复用和事件处理分离。

```
                    ┌─────────────┐
                    │   Reactor   │ ←─ 监听 I/O 事件
                    │  (Selector) │
                    └──────┬──────┘
                           │ 分发事件
              ┌────────────┼────────────┐
              ↓            ↓            ↓
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ Handler  │ │ Handler  │ │ Handler  │
        │  (读)    │ │  (写)    │ │  (连接)  │
        └──────────┘ └──────────┘ └──────────┘
```

**变体**：

- **单 Reactor 单线程**：简单但有性能瓶颈
- **单 Reactor 多线程**：事件分发和业务处理分离
- **主从 Reactor**：Netty 采用的模式，主 Reactor 处理连接，从 Reactor 处理读写

**代表框架**：Netty、Mina、Redis（单线程 Reactor）

### 5. Proactor 模式

**模型**：异步操作完成后，结果已经就绪，直接交给处理器。

```
Thread-1 ──→ Proactor.initiateRead() ──→ OS 异步读取
                                              ↓
                              OS 完成后将数据放入 buffer
                                              ↓
                              Proactor 回调 Handler.handle(buffer)
```

**与 Reactor 的区别**：

- Reactor：通知"可以读了"，需要应用自己读
- Proactor：通知"已经读完了"，数据已就绪

**代表实现**：Windows IOCP、Boost.Asio

### 6. 半同步/半异步模式（Half-Sync/Half-Async）

**模型**：异步层处理 I/O 事件，同步层通过线程池处理业务逻辑。

```
异步层（I/O 线程）──→ 收到数据 ──→ 放入队列
                                      ↓
同步层（工作线程池）──→ 从队列取数据 ──→ 业务处理
```

**特点**：

- I/O 线程轻量，只做数据收发
- 业务逻辑在独立线程池执行，不阻塞 I/O
- ACE 框架的经典模式

### 本项目为何选择 BIO？

| 因素 | BIO | NIO | Netty |
|------|-----|-----|-------|
| 连接数 | 少（< 100） | 多（> 10000） | 多 |
| 编程复杂度 | 低 | 高 | 中 |
| 依赖 | 无 | JDK 内置 | 第三方库 |
| 调试难度 | 低 | 高 | 中 |
| 适用场景 | 仪器通信 | Web 服务器 | 通用高并发 |

仪器通信场景的典型特征：

1. **连接数少**：通常只连接 1~几台仪器
2. **请求-响应模式**：发一条命令，等一个响应
3. **长连接**：连接建立后长时间保持
4. **低并发**：不需要同时处理大量请求
5. **可维护性优先**：代码简单直观比极致性能更重要

因此 BIO 是最合适的选择。如果未来需要支持大规模连接，可以平滑迁移到 Netty。

# TCP 协议深度解析

## 一、TCP 三次握手

```
客户端                              服务器
  │                                   │
  │──── SYN (seq=x) ────────────────►│  (1) 客户端发起连接
  │                                   │
  │◄─── SYN+ACK (seq=y, ack=x+1) ───│  (2) 服务器确认并发起反向连接
  │                                   │
  │──── ACK (ack=y+1) ──────────────►│  (3) 客户端确认
  │                                   │
  │════════ ESTABLISHED ═════════════│  连接建立，可双向传输
```

**本项目对应**：`TcpConnection.connect()` → `Socket.connect(address, timeout)` 触发三次握手。

为什么是三次？两次不行吗？
- 两次握手无法防止历史重复连接请求（已失效的 SYN）导致服务器误建连接。
- 第三次 ACK 确认客户端确实存在且愿意建立连接。

## 二、TCP 四次挥手

```
客户端                              服务器
  │                                   │
  │──── FIN ────────────────────────►│  (1) 客户端请求关闭
  │                                   │
  │◄─── ACK ─────────────────────────│  (2) 服务器确认
  │                                   │
  │         [服务器继续发送剩余数据]      │  半关闭状态
  │                                   │
  │◄─── FIN ─────────────────────────│  (3) 服务器请求关闭
  │                                   │
  │──── ACK ────────────────────────►│  (4) 客户端确认
  │                                   │
  │         TIME_WAIT (2MSL)          │  客户端等待 2MSL 后关闭
```

**本项目对应**：`TcpConnection.close()` → `Socket.close()` 触发四次挥手。

为什么是四次？不是三次？
- TCP 是全双工，每个方向独立关闭。FIN 只表示"我不再发数据"，对方仍可继续发。
- 服务器收到 FIN 后可能还有数据没发完，所以 ACK 和 FIN 分两步。

## 三、TCP 状态机

```
                              ┌─────────┐
                    ┌────────►│CLOSED   │
                    │         └─────────┘
                    │              │ active open
                    │              ▼
                    │         ┌─────────┐
                    │         │SYN_SENT │──── 超时/被拒 ────┐
                    │         └─────────┘                   │
                    │              │ 收到 SYN+ACK           │
                    │              ▼                        │
              close │         ┌─────────┐                  │
                    │    ┌───►│ESTABLISHED│◄─── 连接建立 ───┘
                    │    │    └─────────┘
                    │    │         │ close
                    │    │         ▼
                    │    │    ┌─────────┐
                    │    │    │FIN_WAIT_1│
                    │    │    └─────────┘
                    │    │         │ 收到 ACK
                    │    │         ▼
                    │    │    ┌─────────┐     收到 FIN
                    │    │    │FIN_WAIT_2│──────────────┐
                    │    │    └─────────┘               │
                    │    │         │                    │
                    │    │         ▼                    ▼
                    │    │    ┌─────────┐         ┌─────────┐
                    │    └────│TIME_WAIT│◄────────│CLOSING  │
                    │         └─────────┘         └─────────┘
                    │         │ 2MSL 超时
                    └─────────┘
```

**本项目简化状态机**：`ConnectionState` 枚举定义了 NEW → CONNECTING → CONNECTED → DISCONNECTED → CLOSING → CLOSED，将 TCP 的 11 个状态简化为 6 个对应用有意义的逻辑状态。

## 四、Socket 选项详解

| 选项 | 系统调用 | 默认值 | 说明 |
|------|---------|--------|------|
| TCP_NODELAY | setsockopt TCP_NODELAY | false | 禁用 Nagle 算法。仪器通信报文短小，本项目默认 true |
| SO_KEEPALIVE | setsockopt SO_KEEPALIVE | false | TCP keepalive 探测。本项目默认 true |
| SO_RCVBUF | setsockopt SO_RCVBUF | OS 默认 | 接收缓冲区大小。本项目默认 8192 |
| SO_SNDBUF | setsockopt SO_SNDBUF | OS 默认 | 发送缓冲区大小。本项目默认 8192 |
| SO_TIMEOUT | set SO_TIMEOUT | 0（无限） | 读超时（毫秒），仅影响 read() |
| SO_REUSEADDR | setsockopt SO_REUSEADDR | false | 允许重用 TIME_WAIT 端口。本项目设为 true |
| SO_LINGER | setsockopt SO_LINGER | -1（禁用） | 控制 close() 行为。-1=优雅关闭, 0=RST, >0=等待 |

### Nagle 算法

Nagle 算法的核心思想：如果发送方有未确认的小包，则缓存后续小数据，直到收到 ACK 或积累到足够大的包再发送。

```
无 Nagle（TCP_NODELAY=true）：
  write(1B) ──→ 立即发送
  write(1B) ──→ 立即发送
  write(1B) ──→ 立即发送

有 Nagle（TCP_NODELAY=false）：
  write(1B) ──→ 发送
  write(1B) ──→ 缓存（等待 ACK）
  write(1B) ──→ 缓存
  收到 ACK ──→ 一起发送缓存的 2B
```

仪器通信场景：命令短小、要求实时响应，因此本项目默认开启 TCP_NODELAY 禁用 Nagle。

### SO_LINGER 详解

```
linger = -1（默认）：
  close() ──→ 立即返回 ──→ 内核后台发送缓冲区残留数据 ──→ 正常四次挥手

linger = 0：
  close() ──→ 立即返回 ──→ 丢弃缓冲区数据 ──→ 发送 RST ──→ 连接重置

linger = 5：
  close() ──→ 阻塞最多 5 秒 ──→ 等待数据发送完毕 ──→ 超时则发送 RST
```

# Java 并发编程要点（本项目涉及）

## 一、锁策略

### ReentrantLock vs synchronized

| 特性 | synchronized | ReentrantLock |
|------|-------------|---------------|
| 公平性 | 非公平 | 可选公平/非公平 |
| 可中断 | 不可 | `lockInterruptibly()` |
| 超时获取 | 不可 | `tryLock(timeout)` |
| 条件变量 | `wait/notify` | `Condition` |
| 释放 | 自动（作用域退出） | 手动（finally 中 unlock） |

**本项目选择**：`ReentrantLock(true)`（公平锁），确保请求按到达顺序获取锁，避免饥饿。

### 双锁设计

```
requestLock：保护"检查 pending → 注册 → 写入命令"
  ┌─────────────────────────────────────────┐
  │ if (hasPending()) throw ...             │
  │ pending = requestManager.register(...)  │
  │ connection.write(encoder.encode(...))   │
  │ response = pending.future().get(...)    │
  └─────────────────────────────────────────┘

lifecycleLock：保护连接生命周期
  ┌─────────────────────────────────────────┐
  │ connect() / disconnect() / close()      │
  │ 状态转换、Socket 操作、线程启停          │
  └─────────────────────────────────────────┘
```

两把锁的获取顺序：`requestLock` → `lifecycleLock`（如果需要同时获取），避免死锁。

## 二、volatile 与 happens-before

```java
// TcpConnection 中的 volatile 字段
private volatile Socket socket;
private volatile InputStream input;
private volatile OutputStream output;
private volatile ConnectionState state;

// InstrumentClientImpl 中的 volatile 字段
private volatile Receiver receiver;
private volatile Thread receiverThread;
private volatile boolean closed;
private volatile boolean reconnectSuppressed;
```

**volatile 保证**：
1. **可见性**：写线程对 volatile 变量的写入，对读线程立即可见
2. **有序性**：编译器和处理器不会对 volatile 读写重排序
3. **happens-before**：volatile 写 → 后续 volatile 读，建立 happens-before 关系

**典型应用**：Receiver 线程写 `running = false`，主线程读 `running` 检查是否退出。

## 三、CAS 与原子操作

```java
// RequestManager：CAS 注册 pending 请求
if (!pending.compareAndSet(null, request)) {
    throw new IllegalStateException("another request is already pending");
}

// InstrumentClientImpl：CAS 防止重复调度重连
if (reconnectScheduled.getAndSet(true)) {
    return; // 已有重连任务在调度中
}

// PendingRequest：CAS 防止重复完成
if (!completed.compareAndSet(false, true)) {
    return false; // 已被超时线程完成
}
```

CAS 的优势：无锁、无阻塞、适合低竞争场景。本项目在"单 pending 请求"、"重连调度标志"等低竞争场景使用 CAS。

## 四、CopyOnWriteArrayList

```java
// 监听器列表使用 CopyOnWriteArrayList
private final CopyOnWriteArrayList<ConnectionListener> connectionListeners;
private final CopyOnWriteArrayList<DataListener> listeners;
private final CopyOnWriteArrayList<ClientInterceptor> interceptors;
```

特点：写时复制，读无锁。适合"读多写极少"的场景（监听器注册/移除很少，回调频繁）。

## 五、LongAdder 无锁计数

```java
// ClientMetrics 使用 LongAdder 而非 AtomicLong
private final LongAdder sentFrames = new LongAdder();
private final LongAdder sentBytes = new LongAdder();
```

`LongAdder` vs `AtomicLong`：
- `AtomicLong`：所有线程 CAS 竞争同一个值，高并发下性能差
- `LongAdder`：每个线程维护独立 Cell，最终求和，高并发下性能好

本项目指标收集使用 `LongAdder`，适合多线程频繁更新的场景。

## 六、CompletableFuture

```java
// PendingRequest 使用 CompletableFuture 等待响应
private final CompletableFuture<Response> future = new CompletableFuture<>();

// 超时线程：completeExceptionally
// Receiver 线程：complete
// 调用线程：get(timeout) 阻塞等待
```

`CompletableFuture` 的优势：
- 异步编程模型，支持链式回调
- `complete()` / `completeExceptionally()` 线程安全
- 与 `requestAsync()` 天然配合

## 七、线程池与优雅关闭

```java
private void shutdownExecutorGracefully(ExecutorService executor, String name) {
    executor.shutdown();                           // 不再接受新任务
    try {
        if (!executor.awaitTermination(3, TimeUnit.SECONDS)) {
            executor.shutdownNow();                // 强制中断
            if (!executor.awaitTermination(1, TimeUnit.SECONDS)) {
                log.error("{} failed to terminate", name);
            }
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        executor.shutdownNow();
    }
}
```

关闭策略：先 `shutdown()` 等待任务完成 → 超时则 `shutdownNow()` 中断任务 → 再超时则记录错误。

# ByteBuffer 使用范式（LengthFieldProtocol 解码器）

## 核心概念

```
position：当前读写位置
limit：有效数据边界
capacity：缓冲区总容量
```

## 两种工作模式

```
写模式（put 后）：
[已写入数据][待写入区域]
  ^        ^
position   capacity=limit

读模式（flip 后）：
[已读][待读数据][未使用]
  ^     ^        ^
pos   limit   capacity
```

## 关键方法

| 方法 | 功能 | 状态变化 |
|------|------|---------|
| `flip()` | 切换写模式→读模式 | limit=position, position=0 |
| `compact()` | 压缩已读数据，保留未读数据 | 未读数据前移, position=remaining, limit=capacity |
| `clear()` | 重置缓冲区 | position=0, limit=capacity（不清空数据） |
| `remaining()` | 获取剩余可读字节数 | 返回 limit - position |

## 本解码器工作流程

```
1. put(data) 后：position=数据长度, limit=1024（写模式）
2. flip() 后：position=0, limit=数据长度（读模式）
3. 处理完一帧后 compact() 后：未处理数据前移, position=未处理数据长度（写模式）
```
