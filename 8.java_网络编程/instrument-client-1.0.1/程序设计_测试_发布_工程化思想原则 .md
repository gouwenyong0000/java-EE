# 程序设计、测试与发布：工程化思想原则

对于 Java Socket 客户端这类涉及网络通信、并发、协议解析和资源管理的程序，工程质量不能只看功能是否实现，还要看程序是否**容易理解、容易测试、面对异常能否恢复、变更是否可控、发布是否可靠**。

可以把整个软件工程过程归纳为三个阶段：设计阶段降低复杂度，测试阶段验证正确性，发布阶段控制风险。

## 一、程序设计原则

### 1. 核心思想

| 原则 | 核心含义 | 实践方法 |
|---|---|---|
| 单一职责原则（SRP） | 一个模块尽量只承担一种职责 | 通信、协议、业务适配分别设计 |
| 高内聚、低耦合 | 模块内部关联紧密，模块之间依赖少 | 通过接口定义模块边界 |
| 依赖倒置（DIP） | 高层逻辑不依赖底层实现细节 | 业务依赖通信接口，而不是直接操作 Socket |
| 开闭原则（OCP） | 扩展功能时尽量不修改稳定代码 | 通过解码器接口扩展不同协议 |
| 组合优于继承 | 优先组合多个独立能力，而非构建复杂继承树 | 将重试、编解码、连接管理独立组合 |
| KISS | 保持设计简单 | 不为尚未出现的需求过度设计 |
| DRY | 避免重复维护同一份逻辑 | 统一配置校验、帧解析、错误处理 |
| YAGNI | 不提前实现没有实际需求的功能 | 不为了可能的未来需求引入复杂框架 |

### 2. 架构设计原则

结合 Socket 客户端，可以按以下职责划分模块：

- **接口层（API / Contract）**：统一调用方式、参数约束、异常语义。
- **业务适配层（Application）**：命令编排、请求匹配、业务语义。
- **协议层（Protocol）**：编码、解码、帧边界、校验。
- **通信层（Transport）**：连接、读写、超时、重连。

这套分层的核心是：**每层只处理自己应该解决的问题，通过明确的契约协作。**

例如：

- TCP 只提供字节流，不保证一次读取就是一条完整消息。
- 协议层负责将字节流还原为完整的数据帧。
- 业务层负责判断响应是否对应当前命令。
- 接口层负责向调用方提供一致、可理解的行为。

### 3. 健壮性与安全性原则

| 原则 | 具体要求 |
|---|---|
| 输入不可信 | 校验配置、命令参数、帧长度、数组范围 |
| 资源有始有终 | Socket、流、线程、执行器均有明确的生命周期 |
| 超时必须明确 | 连接、读取、请求等待分别定义超时语义 |
| 失败必须可解释 | 区分连接失败、协议错误、业务拒绝和响应超时 |
| 重试必须有边界 | 限制次数、等待时间和重试范围 |
| 并发必须有约束 | 明确线程安全、请求关联、队列容量及背压策略 |
| 状态必须一致 | 断连、重连、关闭时统一管理连接状态 |
| 内存必须有上限 | 防止异常数据、超长帧和积压队列耗尽内存 |
| 日志必须克制 | 记录必要上下文，避免泄露口令、密钥及敏感数据 |
| 失败必须可恢复 | 明确哪些异常可以恢复，哪些必须终止或交由调用方处理 |

特别要记住：**TCP 保证的是有序可靠的字节传输，不是业务命令只执行一次。**

例如，客户端发送命令后连接断开，可能是设备已经执行命令但响应丢失。盲目重试可能造成重复操作。涉及设备控制或状态变更时，需要考虑幂等性、请求编号、设备端去重能力，以及超时后的结果确认机制。

## 二、测试设计原则

### 1. 测试的目标不是证明程序没问题

测试的真正目标是：**尽可能早地发现问题，并用可重复的方式证明关键行为符合预期。**

| 原则 | 含义 | 实践方法 |
|---|---|---|
| 测试左移 | 越早发现问题，修复成本通常越低 | 编码过程中就编写测试 |
| 测试金字塔 | 单元测试多，集成测试适量，端到端测试有针对性 | 优先覆盖独立逻辑 |
| 边界优先 | 问题经常出现在边界条件 | 测试空值、极限长度、超时、溢出 |
| 故障注入 | 主动制造故障，验证恢复能力 | 模拟断连、延迟、异常响应 |
| 确定性 | 相同输入和环境应得到可预测结果 | 避免依赖真实时间、外部设备和随机状态 |
| 独立性 | 一个测试不应依赖另一个测试的执行结果 | 每个测试自行准备并清理资源 |
| 可重复性 | 同一个缺陷可以稳定复现 | 固定测试数据、控制并发和时序 |
| 回归保护 | 修复的问题不能在后续版本中重新出现 | 每个重要缺陷都补充回归测试 |

### 2. 测试分层

#### 单元测试（Unit Test）

数量通常最多，运行速度快。测试帧编码与解码、CRC 校验、配置校验、请求匹配、重试策略等独立逻辑。

#### 集成测试（Integration Test）

验证模块协作是否正确。使用本地模拟服务端，测试连接、收发、半包、粘包、超时、断连、重连和资源释放。

#### 端到端与设备验收测试（E2E / Acceptance）

验证真实运行环境下的业务行为。使用真实仪表或等效环境验证协议兼容性、设备响应、长时间运行和异常恢复。

### 3. Socket 客户端必须重点覆盖的测试场景

| 测试类别 | 典型场景 | 重点验证 |
|---|---|---|
| 协议解析 | 半包、粘包、多帧连续到达 | 帧边界正确 |
| 数据异常 | 垃圾字节、错误 STX、非法长度、校验失败 | 不越界、不死循环、不无限占用内存 |
| 网络异常 | 连接拒绝、连接重置、读超时、服务端重启 | 状态正确、恢复行为符合预期 |
| 并发场景 | 多线程同时发送、响应乱序、并发关闭 | 不串包、不错误关联响应、不死锁 |
| 资源管理 | 初始化失败、运行中关闭、重复关闭 | 线程、Socket 和缓冲区正确释放 |
| 重试机制 | 连续失败、恢复后重试、响应丢失 | 次数有上限，不重复执行非幂等命令 |
| 长时间运行 | 持续收发、网络间歇性波动 | 无持续内存增长、线程泄漏或队列积压 |
| 安全边界 | 超长帧、恶意输入、异常日志内容 | 资源消耗受控、敏感数据不泄露 |

### 4. 测试质量不能只看覆盖率

代码覆盖率高，不代表关键风险已经被验证。

例如，解码器的测试即使覆盖了每一行代码，也可能没有验证以下情况：

- 一条数据帧被拆成多个 TCP 数据段到达。
- 多条数据帧一次性到达。
- 帧头前存在噪声，且噪声跨越缓冲区边界。
- 帧长度超过限制或整数计算发生溢出。
- 关闭操作与读写操作同时发生。

更好的标准是：**关键需求有测试，关键异常有测试，修复过的缺陷有回归测试。**

测试还应使用断言验证实际结果，而不是仅验证程序没有抛出异常。

## 三、软件发布原则

### 1. 发布的核心思想

发布不是简单地打一个 ZIP 或 JAR 包，而是将一个已经验证、可追溯、可部署、可回退的版本交付出去。

| 原则 | 核心含义 | 实践方法 |
|---|---|---|
| 可重复构建 | 相同源码和依赖条件下能够重现构建结果 | 固定 JDK、依赖版本和构建配置 |
| 版本可追溯 | 可以确定软件由哪份源码构建 | Git 标签、版本号、提交记录 |
| 发布前验证 | 不把未经验证的代码直接交付 | 自动化构建、测试、静态检查 |
| 依赖可控 | 依赖变化不能悄悄破坏程序 | 固定依赖版本，检查漏洞和兼容性 |
| 配置外置 | 环境差异不应迫使修改源码 | 配置文件、环境变量、参数校验 |
| 制品完整 | 交付物应包含运行所需内容和说明 | JAR、依赖、配置模板、README |
| 失败可回退 | 新版本出问题时能够恢复旧版本 | 保留上一个稳定版本及其配置 |
| 变更可审计 | 能查清版本改了什么、为何修改 | 变更日志、问题记录、发布说明 |

### 2. 推荐的发布流水线

1. 提交代码
2. 代码审查
3. 编译与静态检查
4. 单元测试
5. 集成测试
6. 打包与制品校验
7. 测试环境验收
8. 发布审批
9. 正式部署
10. 健康检查与监控
11. 确认发布；若异常则回滚或停止发布

并非所有项目都需要复杂的 CI/CD 平台，但每个项目都应该具备这些环节对应的检查机制。小型项目可以通过 Maven、Git 和简单脚本实现。

### 3. 发布前检查清单

#### 代码与构建

- [ ] 代码已审查，版本号和变更记录已更新
- [ ] 干净环境下编译成功
- [ ] 自动化测试全部通过
- [ ] 依赖版本和构建配置可追溯

#### 安全与配置

- [ ] 没有将密钥、口令等敏感信息打包进去
- [ ] 生产配置与测试配置已区分
- [ ] 日志级别和敏感数据输出已检查
- [ ] 超时、重试、队列及缓冲区限制合理

#### 部署与恢复

- [ ] 制品完整且可以正常启动
- [ ] 部署步骤与配置说明完整
- [ ] 具备健康检查和故障排查方式
- [ ] 旧版本制品可用，回滚方案明确

## 四、贯穿整个生命周期的工程思想

| 思想 | 要回答的问题 | 核心要求 |
|---|---|---|
| 契约优先 | 模块之间如何协作？ | 明确输入、输出、异常、状态及线程安全约定 |
| 防御式编程 | 遇到非法输入怎么办？ | 在边界处校验，不依赖调用方永远正确 |
| 故障隔离 | 一个模块出错是否会拖垮整个程序？ | 控制影响范围，避免错误无限传播 |
| 显式优于隐式 | 程序的行为是否容易理解？ | 明确超时、重试、状态转换和资源所有权 |
| 最小权限 | 模块是否拥有不必要的能力？ | 限制权限、资源和可执行操作 |
| 可观测性 | 发生问题后能否定位？ | 提供结构化日志、关键指标和错误上下文 |
| 自动化 | 能否减少人工操作和人为失误？ | 自动测试、构建、打包及发布校验 |
| 持续改进 | 如何防止同类问题再次发生？ | 缺陷复盘、补充测试、更新文档和检查规则 |

## 五、以 Java Socket 客户端为例，如何落地

1. **设计阶段：先定义契约，再实现功能。**  
   明确通信接口、协议格式、超时语义、线程安全约定、连接状态机及资源所有权，避免先写代码、后补架构。

2. **实现阶段：先保证正确，再优化性能。**  
   先正确处理 TCP 字节流、半包粘包、断连、并发和资源关闭，再考虑减少数组拷贝、优化 `ByteBuffer` 和内存分配。

3. **测试阶段：先测正常路径，再测异常路径。**  
   使用本地模拟服务端验证协议和网络行为，主动制造超时、断连、非法帧、并发关闭等故障。

4. **审查阶段：不仅检查代码，还检查行为。**  
   重点审查死锁、竞态、资源泄漏、无限重试、内存无界增长，以及重试造成的重复命令执行。

5. **发布阶段：先验证制品，再交付使用。**  
   从干净环境重新构建，运行自动化测试，核对配置和依赖，生成版本说明，并准备回滚方案。

6. **维护阶段：让每次修复都留下保障。**  
   每发现一个重要缺陷，都尽可能增加一个能够复现它的测试用例，防止后续修改再次引入相同问题。

对于 Maven 项目，可以把基本验证流程固定下来：

```bash
# 1. 清理并运行测试
mvn clean test

# 2. 执行完整验证并打包
mvn clean verify

# 3. 查看依赖树
mvn dependency:tree

# 4. 生成发布制品
mvn package
```

注意：`verify` 会执行生命周期中到 `verify` 阶段的绑定任务，但它不会自动替代所有安全扫描、真实设备验收或发布审批。正式发布仍需根据项目要求配置相应检查。

## 六、最后浓缩为十条原则

1. **设计要简单：** 不过度设计，不把简单问题复杂化。
2. **职责要清晰：** 每个模块只承担明确的职责。
3. **边界要明确：** 接口、状态、异常和资源所有权必须清楚。
4. **输入要校验：** 不信任外部输入，也不假设网络数据完整。
5. **资源要受控：** 内存、线程、队列、连接和重试都应有边界。
6. **失败要可预期：** 明确超时、断连、恢复和不可恢复错误的处理方式。
7. **测试要可重复：** 自动化验证正常路径、边界条件和故障场景。
8. **修改要有回归保护：** 修复缺陷时同步补充测试。
9. **发布要可追溯：** 每个版本都能定位源码、依赖、配置和变更。
10. **问题要可恢复：** 出现故障时能定位、止损、恢复或回滚。

**最核心的一句话：好的工程不是让程序永远不出错，而是让错误尽可能早地被发现、影响受到控制、原因能够定位，并且系统能够安全地恢复。**
